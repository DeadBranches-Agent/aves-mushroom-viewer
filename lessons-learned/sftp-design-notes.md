# SFTP feature — design notes that are not obvious from the code

One-line summary: why the sftp module is shaped the way it is, and the traps future changes must not reintroduce.

- **Local-file substitution is the load-bearing trick.** Kotlin already handles `file://` end-to-end (vaults). Full images, regions, and sized thumbnails of downloaded files all work by writing original bytes to the app-internal cache and re-issuing the exact same platform op with the local URI. Do not add sftp awareness to the Kotlin decoding layer; it is not needed.
- **Synthetic album path.** Entries carry `path = <filesDir>/sftp/<host name>/<filename>` purely so `StoredAlbumFilter`'s `entry.directory == album` predicate groups them. Nothing exists at that path. `canEdit` stays false automatically because the path is neither MediaStore nor vault, which is the entire read-only story.
- **Entries are stamped `catalogMetadata` at creation** (dated by remote mtime). Without this, the analysis pipeline would try platform metadata fetches on `sftp://` URIs and fail per entry.
- **EXIF preview orientation:** IFD1 preview bytes carry no orientation. `_withBakedOrientation` injects a minimal EXIF APP1 with the main image's orientation code; Flutter's (Skia's) JPEG decoder honors it. Without this, thumbnails of portrait photos render sideways.
- **Thumbnail pause/resume must mirror `servicePolicy` semantics**: a paused request keeps its completer pending (never errors) and re-runs on `resumeLoading`. Completing the future with an error on scroll-away poisons the Flutter image cache with errored entries.
- **`ThumbnailProviderKey` has no `sizeBytes`**, so byte requests can't build the cache key alone — hence the `_entriesByUri` registry fed by both the DB loader (`_loadSftpEntries`) and `refreshHost`. If an entry is not registered, thumbnail loads throw `StateError` by design (internal invariant, not a network condition).
- **Changed remote file = replace, not update.** `refreshHost` removes and re-creates the entry when mtime/size differ, so every downstream cache keyed on `(path, mtime, size)` — ours, Glide's signature, `ThumbnailProviderKey.dateModifiedMillis` — invalidates by construction.
- **dartssh2 facts:** the host key verify callback may return a `Future` (transport awaits it), and the fingerprint arrives pre-formatted as OpenSSH `SHA256:<base64>` bytes. The verify callback must not throw — capture the refusal and rethrow after the handshake fails (done in `connection.dart`).
- **Platform file ops silently no-op on `sftp://` URIs.** Kotlin's `ImageProviderFactory.getProvider` maps URI scheme → provider and returns null for unknown schemes; the op stream then reports the entry as unsuccessful without any error. Any future destructive/mutating action on sftp entries (like delete does now) must intercept in Dart *before* the delegates route into `mediaEditService`/`MoveType.toBin` — never rely on the platform op failing loudly. Also note the two delete gates differ: the viewer checks `entry.canEdit` per entry, the multi-select delete button has no per-entry gate at all.
- **Known v1 limits (deliberate):** embedded-preview shortcut is JPEG-only (HEIC/AVIF/RAW/etc. fall back to full download at lowest priority); no progressive-JPEG/interlaced-PNG first-pass decode; SVG and camera-raw files are excluded from listings; non-JPEG entries have 0×0 dimensions until their first full download (viewer may briefly lay out with aspect 1); grid speculation estimates indices from scroll fractions, which is approximate under section headers.
